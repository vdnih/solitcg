## 1. ゾーン定義

| ゾーン | 定数名 | 上限 | 性質 |
|---|---|---|---|
| 手札 | `hand` | 制限なし | プレイヤー参照可能 |
| デッキ | `deck` | 40 枚（構築済み） | 非公開・順序あり |
| 場 | `board` | 制限なし | 表向き永続ゾーン |
| ドメイン | `domain` | 1 枚 | 手札からのプレイ時に `FieldRule.playDomain` が置換を管理（§6）。`set_domain` op は未実装（下記参照） |
| 墓地 | `grave` | 制限なし | 順序あり（直近が末尾） |
| エクストラ | `extra` | 10 枚 | ADR-006 によりゾーンとしては維持。編入可能なカードタイプは §4 参照（現状は該当タイプが無く未使用） |
| 除外 | `banish` | 制限なし | ADR-006 で追加を決定。**未実装**（Issue 予定）。ゾーンとしての位置づけのみ本バージョンで確定し、対象となる op は今後追加する |

## 2. ゲーム開始時処理

1. プレイヤーはデッキ（40 枚）をシャッフルする。
2. デッキの上から 5 枚を手札に加える。

## 3. ターン構成（1ターンで完結。PDR-001）

このゲームは**1ターンで完結する**ものとして設計する（`docs/pdr/PDR-001-...md`）。2ターン目のプレイは考慮しない。

- ドロー → メインフェイズ（カードのプレイ・能力発動を自由に行う） → ターン終了。
- ターン終了時に勝敗判定を行う（§12）。ターン終了とゲーム終了は別の状態であり、
  「ターンが終わった」ことと「ゲームが終わった（勝敗が付いた）」ことは演出上も区別する。

> **現状の実装状況**: ターン終了操作・終了時の勝敗判定はまだ実装されていない
> （プレイヤーはいつでも任意の順序でカードをプレイ・発動でき、行動回数の制限もない）。
> 実装は別 Issue（E-3）で行う。
>
> `GameState.activatedThisTurn`（§11 参照）は一度セットされると**ゲーム中ずっと保持され、
> リセットされる契機がない**（旧 `drawPhase()` がリセット処理を持っていたが、呼び出し元が
> なく死蔵コードだったため削除済み）。1ターン完結モデルの下では、これは「1ターンに1度」ではなく
> **「1ゲームに1度」が正しい仕様**であり、リセット処理を新設する必要はない
> （ADR-006 の裁定により、既知の制限ではなく仕様として確定）。

## 4. カードタイプ別ふるまいマトリクス

ADR-006 により、カードタイプは4種に統合する。旧 `ritual` / `arcane` / `relic` / `equip` は
挙動差が無く該当カードも0枚だったため廃止する（実装は Issue E-1）。

| type | 場に残るか | プレイ後に墓地へ | HP を持つか | ドメイン制限 |
|---|---|---|---|---|
| monster | yes | no | yes | no |
| spell | no | yes（解決後） | no | no |
| artifact | yes | no | no | no |
| domain | yes（domain ゾーン） | no | no | max 1 |

`stats`（atk/def/hp）は monster のみが持つ。ADR-006 により、現在は表示専用のデッドスキーマ
（`modify_stat` op が未実装のため hp は変動しない）だが、これは削除せず `modify_stat` を
実装して生きたスキーマにする方針とした（Issue E-5、§10 参照）。

## 5. トリガー（発動タイミング）一覧

| when | 発火タイミング | 対象タイプ |
|---|---|---|
| `on_play` | 手札からプレイした直後（サーチ・移動では発火しない） | 全タイプ |
| `on_destroy` | hp ≤ 0 または `destroy` op により破壊された直後 | 全タイプ |
| `on_discard` | 手札から捨て札に置かれた直後 | 全タイプ |
| `activated` | プレイヤーが手動で発動（§3 の通り1ゲーム1度が正しい仕様） | 場にあるカード |
| `on_spell_played` | spell がプレイされるたび（ドメインカードが購読） | domain |

> MVP スコープ外: `on_enter` / `static` / `on_draw` / `on_domain_set`

## 6. ドメインカード置換裁定

新しいドメインカードをプレイした際、すでにドメインが存在する場合の処理順序：

1. 新カードの `on_play` トリガーをキューに追加。
2. 旧ドメインカードを `grave` へ移動。
3. 旧カードの `on_destroy` トリガーをキューに追加。
4. トリガーキューを FIFO で解決する。

> **`summon` / `set_domain` op について**: `OperationExecutor` に op 自体は存在するが、
> どちらも常に failure を返すスタブ実装であり未使用（`summon` はカード実体化ロジック
> 未実装、`set_domain` はカードDB検索ロジック未実装）。現状、場へのカード配置は
> 手札からの直接プレイ（`FieldRule`）のみで行われる。解消は Issue E-9。

## 7. トリガー解決ルール

- **解決順**: FIFO（First In, First Out）。
- **同時発生**: 同一タイミングで複数のトリガーが発生した場合も、発生順（エンキュー順）に自動で解決する。プレイヤーはキューの順序を操作できない（ADR-004）。
- **最大反復数**: `resolveAll()` 1 回の呼び出しで最大 100 回のトリガー処理（無限ループガード）。
- **`pre` 評価タイミング**: 解決時点（エンキュー時ではなく）に評価する。
- **`pre` 失敗時**: そのトリガーはスキップ（再キューしない）。後続トリガーの処理は継続する。

---

## 8. `pre` 条件式の制約

- フィールドや状態の**読み取りのみ**許可。
- `pre` 式内での状態変更（`draw`・`destroy` 等の op 呼び出し）は禁止。
- 評価失敗（構文エラー等）はスキップ扱い。

## 9. デッキ構築ルール

| ルール | 値 |
|---|---|
| メインデッキ枚数 | ちょうど 40 枚 |
| 同名カード（メイン） | 最大 4 枚 |
| エクストラデッキ枚数 | 最大 10 枚 |
| 同名カード（エクストラ） | 最大 1 枚 |
| エクストラ編入可能タイプ | 現状なし（§4 の型統合により旧 ritual / arcane / relic が廃止されたため。ゾーンは ADR-006 により維持し、対象タイプは将来追加する） |
| 同名カードのカウント | メインとエクストラは別カウント |

## 10. HP と破壊ルール

- `monster` のみ `hp` を持つ。
- `hp <= 0` になった瞬間に破壊される（エンドフェイズまで待たない）。
- 破壊時に `on_destroy` トリガーを発火する。
- `on_discard` は手札から捨てられた場合に monster にも発火する。
- `hp` の変動は `modify_stat` op でのみ発生する予定（**未実装**。Issue E-5）。
  未実装の間、`stats` は事実上の表示専用フィールドであり、`hp <= 0` は発火し得ない。

---

## 11. `activated` 能力の制限

- `activated` 能力は `once_per_turn: true`（省略時デフォルト）の場合、一度発動すると
  そのカードインスタンスでは再発動できない（エンジン強制）。
- `once_per_turn: false` の場合、コストが払えれば何度でも発動できる。
- `GameState` の `activatedThisTurn: Set<String>` にカードの `instanceId` を記録する。
- `activatedThisTurn` をリセットする処理は存在しないが、これは PDR-001 の1ターン完結モデルの下では
  **正しい仕様**である（フィールド名の `...ThisTurn` は歴史的な名残であり、実質「1ゲーム1度」を意味する）。

## 12. 勝敗条件

| 条件 | 判定 | 実装状況 |
|---|---|---|
| 効果勝利（無条件） | `win` op が解決された瞬間 | 実装済み |
| 効果勝利（条件付き） | `win_if` op の条件が満たされた瞬間 | 実装済み |
| 効果敗北 | `lose_if` op の条件が満たされた瞬間 | 実装済み |
| ライフ勝利 | 仮想ライフが 0 以下（初期値: 8000） | **未実装**。ライフを増減する op が無く現状到達不能。ADR-006 によりライフは残置・実装する方針（Issue E-4） |
| デッキ勝利 | ターン終了時点で仮想デッキが 0 枚 | **未実装**。ターン終了処理（§3）が無いため判定が走らない。Issue E-3 で成立させる |

> ドロー不能による即時敗北はない。ターン終了時に判定する（ターン終了処理の実装後）。

## 13. 式評価システム（ExpressionEvaluator）

対応する参照子：

| 参照子 | 意味 |
|---|---|
| `hand.count` | 手札の枚数 |
| `deck.count` | デッキの残り枚数 |
| `board.count` | 場のカード枚数 |
| `grave.count` | 墓地の枚数 |
| `domain.exists` | ドメインが存在するか（0/1） |
| `player.life` | 自分のライフ |
| `opponent.life` | 相手のライフ |
| `self.counter('key')` | トリガー発生元カードの `metadata[key]`（`add_counter`/`remove_counter` op で操作） |
| `count(type:'X', zone:'Y')` | 指定ゾーンの指定タイプのカード枚数 |
| `count(tag:'X', zone:'Y')` | 指定ゾーンの指定タグのカード枚数 |
| `field.exists` / `field.count` | `board` の旧名。後方互換のため残置（新規カードでは `board` を使うこと） |

対応する比較演算子（1式につき1つのみ、複合条件は非対応）: `>= <= > < == !=`
比較演算子を含まない式は `値 > 0` として真偽判定される。
複数条件の AND は、`pre` に複数の式を並べることで表現する（`&&`/`||`/前置 `!` は式内では非対応）。

## 14. フィルタシステムとカード選択

### filter パラメータ

`discard`, `move`, `destroy`, `search` の各 op は `filter` パラメータをサポートする。
カードを絞り込む手段はこの `filter` に一本化する（ADR-006。`docs/CARD_YAML_SPEC.md` が
記載していた `"{scope}:{owner}:{selector}"` ターゲット記法は、`destroy` の `choose:*:<type>`
以外未実装だったため廃止した）。

```yaml
filter:
  tag: string    # タグ完全一致
  type: string   # CardType 文字列完全一致（例: monster, spell）
  name: string   # カード名完全一致
```

* 複数キーは AND 条件として評価する。
* `filter` パラメータ自体を省略した場合はフィルタなし（全カードが対象）。

### タグシステム

* `CardData.tags: List<String>` に任意の文字列タグを設定できる。
* YAML: `tags: [tagA, tagB, ...]`
* タグは大文字・小文字を区別する。
* 数の制限なし。

### 各 op での filter と選択挙動

| op | candidates < count | candidates == count | candidates > count かつ filter あり |
|---|---|---|---|
| `discard` | failure | 自動選択して捨て | ChoiceRequest → プレイヤー選択 |
| `move` | 一致分だけ移動 | 自動移動 | ChoiceRequest → プレイヤー選択 |
| `destroy` | 一致分だけ破壊（0件なら failure） | 自動破壊 | ChoiceRequest → プレイヤー選択 |
| `search` | 一致分だけ移動 | 全移動 | 先頭 max 枚を自動移動（選択なし） |

### ChoiceRequest の解決フロー

1. エンジンが `ChoiceRequest` を `GameState.choiceRequest` ValueNotifier にセット
2. `TriggerService.resolveAll()` が一時停止（`GameResult.pending` を返す）
3. ゲーム画面が `ChoiceOverlay` を表示し、候補カードを一覧表示
4. プレイヤーが指定枚数を選択して確定
5. `TCGGame.resolveChoice()` が選択されたカードに操作を適用
6. `choiceRequest` をクリアし、`TriggerService.resolveAll()` を再呼び出し
